## 壁纸自动轮换「看不见」根因诊断（已确认）

- 用户现象：斗战者控制台 UI 背景（非 Windows 桌面壁纸）在托盘区不打开窗口时不轮换。
- 结论：轮换服务**在后端**（`server/api/BackgroundRotationService.cs`，`BackgroundService` 托管进 API 进程，跟着 `Douzhanzhe.API.exe` 独立进程跑，不依赖 Shell 窗口）。用户原以为服务放错到 Shell，是误判。
- 真因：后端只把 `config/background.*` 文件换掉（仅 `source=="network"` 模式会轮换；`local` 单张固定图不轮换），但**前端只在挂载时读一次 `/api/background`**（`App.jsx:66` / `SettingsPanel.jsx:97`），写进 CSS 变量 `--wallpaper-image`，无定时轮询、无 WebSocket 推送、无缓存戳。磁盘图已换，屏幕上看不见。页面重载（重启/后端恢复 Reload/F5）才会重新拉，故"开窗口好像轮换、托盘像冻死"。
- 用户当前模式：网络轮换。属"轮换了但看不见"。
- 修复方向（待用户拍板机制）：后端轮换时往 `background-opts.json` 写 `lastRotated` 时间戳；前端定时（~30s）轮询 `/api/background-opts`，`lastRotated` 变了就用 `/api/background?t=<戳>` 重新 `applyWallpaperCss`。`/api/background` 已 `no-store`，保证拿到新字节。隐藏窗口下 WebView2 JS 仍运行，轮询在托盘态也生效。
- 决议（用户拍板）：**塞进遥测 WS 帧**（零新增流量、延迟≤250ms、托盘态生效），不用独立轮询。

  - 后端 `BackgroundRotationService` 加 `static DateTime? LastRotatedUtc`，轮换成功时写；
  - `TelemetryBackgroundService` 在 250ms 遥测帧加 `bgLastRotated`（Unix 秒）；
  - `Program.cs` `/api/background-opts` GET 返回 `lastRotated` 兜底；
  - 前端 `uxtuAdapter.refreshWallpaperOnRotate(stamp)` 按戳带 `?t=` 重新套用；
  - `useControlState` 遥测 onData 检测戳变化触发刷新。

## 启动慢 + 前端误报"后端未连接" 的根因定位（2026-11-02 15:40-15:55）

## 前端"等好久才有数据"的根因定位 + 修复（2026-11-02 16:00-16:35）

- 用户实测 pre.3：UI 已不阻塞（1.7s 出画面），但仪表盘长时间"暂无实时数据"，左下角"连接中"（backendOnline=null → WS 连上但没收到任何帧，也没报错）。
- **排查手段（可复用）**：用 PowerShell `ClientWebSocket` 直连 `ws://127.0.0.1:3100/ws` 量首帧；用 `netstat -ano` 看连接归属进程；给遥测首帧加**逐项耗时日志**后一次定位。
- **根因 A（首帧 34 秒）**：250ms 一轮的遥测循环里夹着重活，全在**读取路径同步执行**：
  | 项 | 实测耗时 | 原因 |
  |---|---|---|
  | CpuFreq | **33050 ms** | `PerformanceCounter` 首次读要初始化 PerfLib |
  | CpuTemperature/CpuFanRpm/GpuFanRpm | 31/62/62 ms | EC 读（每次 2+5ms sleep × 多寄存器） |
  | KeyboardBrightness | 27 ms | 物理内存读 |
  | Wmi ×4 | 0ms（缓存后） | **每次调用都真发一次 WMI 方法调用** |
  | nvidia-smi ×2 / PowerShell+CIM | 原同步阻塞 | GPU 温度+统计 / 内存 / 磁盘（Get-Disk + WMI ASSOCIATORS 冷启动 5~15s） |
  - 修复：GPU 温度/统计/内存/磁盘采集移到后台线程、属性只读缓存；`CpuFreq` 后台刷新 + `CallNtPowerInformation` 内核快速查询兜底；`WmiInterface` 四个读接口加 2 秒缓存 + 后台刷新（启动 GPU 模式恢复改走 `GetGpuModeFresh()` 拿实时值）。
  - **实测：首帧 35539ms → 2482ms；WS 客户端接入后 ~200ms 收到首帧，之后稳定 ~450ms/帧。**
- **根因 B（推送循环卡死）**：`SendAsync(..., CancellationToken.None)` 无超时。客户端进程被杀/半开时 socket 仍报 Open，缓冲区写满后 SendAsync 永久挂起 → 整个循环卡死 → 所有前端都收不到帧（"等好一会儿才自愈"= 缓冲区写满到 socket 报错的那几十秒）。修复：每客户端 1.5s 发送超时 + 并发发送 + 超时 `Abort` 移除；`NotifyModeSwitch` 的无上限 `.Wait()` 同样加超时。
- **回归 B 的复现方法**（很有效）：客户端 A 连上读几帧 → `Abort()` 强制断开（模拟进程被杀）→ 客户端 B 再连：**修复前 B 永远收不到帧**（循环已被 A 卡死），修复后 B 正常。
- **回归 C（我上轮引入的 bug）**：WebView2 缓存版本戳用 `Application.ProductVersion`，而 Shell csproj 没有 `Version` 属性 → 恒为 1.0.0.0 → 升级后缓存永不清 → 会退回"前端更新后缓存旧版本"的老问题。改读安装目录 `version.txt`。
- 收尾：API/Shell `dotnet build -c Release` 0 错误（仅既有 MSB3277 + CS8600@WndProc）；`npm run build` 通过；vitest 17/17。版本 → 2.0.2-pre.4。
- 备注：测试期间发现一个 10-30 遗留的僵尸 Shell 进程（PID 73084，2026-10-30 启动）一直在跑，kill 需提权失败——它的 WebView2 会持续重连 API，是僵死连接的潜在来源之一，已提醒用户。

## 子进程回收兜底 + 安装静默清理（2026-11-02 16:45-17:00）

- 用户反馈：安装流程有 **6 个一闪而过的命令行窗口**；并要求"安装新版本自动杀旧进程/服务、清理僵尸进程不干净"要兜底，且希望通过安装流程观察自动清理效果。
- **重要更正（我连着判断错了两次）**：那 37 个遗留 msedgewebview2 **不是我们的** —— 命令行显示 `--webview-exe-name=SearchHost.exe`、`--user-data-dir=...MicrosoftWindows.Client.CBS_cw...`，属于 Windows 搜索 / Windows 更新客户端 / cc-switch / piliplus / GameViewer / wetype_update。父进程 PID 是**复用**的（我们的 Shell 早死了，PID 被别的程序占用），所以**不能按父进程判断归属**。⇒ 唯一可靠标识是命令行里含我们专属 `--user-data-dir=…\Douzhanzhe Console\WebView2`。之前给用户的清理脚本按"创建时间早于昨天"筛选会误杀 Windows 组件，已重写为只按 user-data-dir 匹配。
