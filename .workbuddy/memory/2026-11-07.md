### 关键技术结论

- 精确编码（`PresetCommandBuilder.BuildCoperArg`）：`ccd<<28 | (core/8)<<24 | (core%8)<<20 | encoded20`，负值 `0x100000-abs`，正值原值。示例 ccd1/core7/-30 → `0x107FFFE2`。

### 本轮发现的两个真实缺口（别再当成「已验证」）
1. **睡眠恢复根本不存在**：`RestoreAllPerfSettings` 全仓库只有 `"Startup"` 和 `"switch"` 两个调用点；`TelemetryBackgroundService` 的 `RecoverAfterSleep` 只恢复风扇曲线。注释写「启动 + 睡眠恢复共用」是误导。而逐核重放被有意排除在 `ParameterGuard` 之外 → **睡眠唤醒后若 SMU 被复位，逐核 CO 不会自动恢复**。需要补 PowerModeChanged 重放或降低周期重放频率（待用户决策，未擅自改）。
2. **SMU 状态码缺负向对照**：上面的 9 个负向对照验证的是「后端校验层」有区分度，**不是固件**。仍存在「固件对任何参数都回 0x01」的假阳性可能，因此 `16/16 0x01` 只能说明命令被接受，不能说明逐核值真的落到对应核心。间接证据仅有：非管理员时 `probe:false` vs 提权后 `probe:true`。

### 每核不同负压的能力边界
UI 每核独立滑块 / API `offsets` 数组 / 编码 core 位段 / 持久化数组 / 16 核交错值实测全被接受 —— **能下发不同值**；但无 `get-coper` 读回、无 VID 观测、核心编号 ↔ APIC ID 映射未验证 —— **不能证明每核实际生效值不同**。

## 第四轮：加 CPU 负载后确认负压生效（13:08–13:15）

用户指出「空闲态电压不算有效成绩，不一定按负压设定来，加 CPU 负载才能确定」—— 完全正确，上一轮把 0.58V CC6 睡眠电压混进中位数了。

### 方法
`%TEMP%\zm_ab2.py`：16 个 `multiprocessing` CPU-bound 进程稳定满载 → 全 0 → 16 核交错 -15/-5 → 归零，各采样 8 次保留**原始样本**（不再只存中位数）。过滤条件 `volt>0.62 && c0>50 && clk>2.0`（排除 CC6 睡眠态），有效样本 A 84/88、B 85/88、C 72/88。
关键修正：全核满载撞 50W STAPM 墙时频率被压到 3.2–3.35GHz，**VID 稳定在 0.68–0.71V，不是轻载 boost 的 0.9V**；第一次用 `volt>0.75` 过滤把 92% 有效样本误砍了，阈值应为 0.62。

### 结论（CO 生效）
- 三阶段负载一致：STAPM 50.0W、温度 70.5/70.5/70.2°C、活跃核 c0=100% → 排除负载/温度漂移。
- **A→B：11/11 核 VID 全部下降，中位 -0.0177V（范围 -0.0221~-0.0030），而频率还略升 +0.038GHz**；**B→C：11/11 核回升 +0.0441V**。频率升而电压降，是 CO 生效的特征。
- 两组不同负压产生可区分响应档：标 -15 组 dV 中位 -0.0033V、标 -5 组 -0.0181V，组内数值高度一致 → 每核不同值确实产生不同电压响应，不只是命令被接受。

### 单核定点验证（解释分组反常）
`%TEMP%\zm_map.py`：只给 `ccd0/core5=-15`（arg=0x005FFFF1，status=0x01/rsmu），结果**仅 ZenMaster 标号 10 的核 VID 降 -0.0322V 且归零回升 +0.0279V**，其余 10 核只有 -0.0048~-0.0096V 背景漂移且不回升。
→ 单核独立生效、可定位、可恢复；`ccd/core` 与 ZenMaster `core` 标签非一一对应（5→10，疑似逻辑处理器/APIC 索引 vs 物理核编号），这解释了分组标签反常。**不改产品代码**（编码遵循 UXTU 标准且确实只作用于唯一物理核），但 UI 标号 ↔ 物理核的精确对应若需要得单独标定。
